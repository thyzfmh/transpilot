# FlashDB C 到 Rust 翻译规范

本规范是 `code/FlashDB` 到 `code/flashDB_rust` 的强制实现约束。脚本负责发现可机械验证的问题，本规范负责约束脚本无法完整表达的语义、布局、状态机和边界设计。

## 规范用语

- “必须”：不满足时不得宣告完成。
- “禁止”：出现时必须修复或给出由 C 源码证明的等价方案。
- “应”：默认执行；只有 C 源码证据表明不适用时才可偏离，并把理由写入合规证据。
- 事实优先级：C 运行结果 > C 测试及断言 > C 头文件、宏和实现 > 注释与文档 > 当前 Rust 实现。
- 当前 Rust 输出不得反向充当预期值或正确性依据。

## BASE-01 源码是唯一语义基准

- 必须从 C 的调用链、条件编译、宏展开、错误分支和测试断言提取行为，不能只按函数名和参数形状翻译。
- 必须先记录源文件、头文件、编译选项、关键宏、模块依赖和翻译顺序，再修改对应 Rust 行为。
- C 源码存在歧义时，必须写最小 C 探针或运行原 C 测试取得可重复的结果；不能凭 Rust 习惯猜测。

## PROF-01 只实现并声明固定配置画像

- 本题验收画像固定为：POSIX 文件模式、KVDB 与 TSDB 同时启用、`FDB_WRITE_GRAN=1`、32 位有符号时间戳。
- 必须按 `tests/fdb_cfg.h` 和实际 C 编译结果确认画像，禁止把未验证的其他后端、写粒度或 64 位时间戳宣称为已支持。
- 所有布局探针、持久化样本、C ABI 类型和边界公式必须与该画像一致；配置漂移时必须在翻译开始前失败。

## IMM-01 输入源码和验证器不可被翻译过程修改

- C 源码、头文件、测试和 Makefile 必须与固定 SHA-256 清单一致；编译产生的对象和临时数据不属于源码修改。
- 目标 `harness/` 必须逐文件等于 Skill 模板，禁止删除测试、放宽阈值、改写预期值或绕过失败命令。
- 任何输入或验证器漂移都必须先恢复固定版本，不能把漂移后的结果当作完成证据。

## COV-01 源模块和行为必须闭合

- `code/FlashDB/src` 下每个 `.c` 文件都必须在 `reports/c-module-coverage.tsv` 中有且仅有一行。
- 每行必须记录关键 C 符号、承接行为的 Rust 文件、验证该模块的 Rust 测试及具体证据。
- 禁止以“入口已实现”“编译通过”代替模块行为覆盖；静态函数、错误路径、持久化路径和清理路径同样属于翻译范围。
- 头文件中的常量、布局、回调类型和公开声明必须由源码清单或模块行覆盖。

## API-01 公开 API 必须逐项闭合

- 必须机械提取 `inc/flashdb.h` 的全部 `fdb_*` 函数以及 `fdb_def.h` 的全部 KVDB/TSDB 控制命令。
- 每个公开函数必须由 release 静态库导出、由 C 运行入口调用、由源码驱动的 Rust 测试覆盖，并绑定成功运行证据。
- 控制命令不能只定义常量；必须保持参数方向、调用时机、回调保存、getter 输出和状态改变语义。
- 打印、检查、反向遍历、容量计算等非主路径 API 禁止以空实现、固定成功或仅满足链接的方式处理。

## TDD-01 必须采用 C 测试优先

- 每个 C `TEST_RUN(...)` 必须先形成独立 Rust 验收测试，再实现使其通过的 Rust 行为。
- Rust 测试必须保留准确的 C case id，并复现 C 测试的初始化、操作顺序、断言和重复执行上下文。
- 预期值只能来自 C 测试、C 宏/常量、C 运行轨迹或机械计算公式。
- 对 C 测试未覆盖但影响公开行为的分支，必须补充源码驱动的边界测试。
- 禁止在实现完成后按 Rust 当前行为补写“自证正确”的测试。

## INT-01 保持 C 的整数和位运算语义

- 必须核对每个持久化字段、地址、长度、时间戳、状态位和 CRC 的 C 类型宽度及有无符号属性。
- 必须显式处理整数提升、截断、溢出、移位、按位取反和符号转换；不能依赖隐式 `as` 转换掩盖边界。
- 地址和磁盘格式字段应保持固定宽度类型，在切片索引边界经过检查后才能转换为 `usize`。
- 对齐、状态表大小和记录长度必须由与 C 宏等价的公式计算，禁止使用只对当前样本成立的常数。

## LAY-01 磁盘格式按字节布局实现

- FlashDB 持久化结构必须视为字节协议，使用显式偏移和小端读写函数；禁止直接序列化普通 Rust 结构体。
- 只有真实 FFI 参数结构才能使用 `#[repr(C)]`，且必须用 C 布局探针验证大小、对齐和字段偏移。
- 必须验证 KVDB sector header、KV header、TSDB sector header、TSL index 的大小和关键偏移。
- 必须保持擦除值、写粒度、padding、magic、CRC 覆盖范围以及状态位在介质上的实际编码。

## STA-01 状态机和遍历顺序必须等价

- sector、KV、TSL、GC 和迭代器必须按 C 的合法状态及转换条件实现，不能只保留最终业务值。
- 状态更新顺序必须保留掉电语义；禁止把多步单向写入折叠为一次高层集合更新。
- 必须覆盖空库、满 sector、跨 sector、重复写、删除后查找、GC 搬移、清理和重复初始化。
- 查询、遍历、回调和停止条件的顺序必须与 C 一致。

## PST-01 持久化和重启语义必须可验证

- 文件后端和内存后端应通过同一核心行为接口，例如 `FlashBackend`，但不得改变 C 可观察行为。
- 必须测试关闭后重新打开、部分状态恢复、删除状态恢复、GC 后恢复和 TSDB 时间顺序恢复。
- 禁止仅在进程内维护权威映射而忽略介质扫描；若使用缓存，介质数据必须仍能独立恢复状态。
- 读写、擦除和边界失败必须沿调用链返回，不得静默成功。

## XIO-01 必须验证 C 与 Rust 双向持久化兼容

- 必须使用同一份 C 调用驱动分别链接原 C 实现和 Rust 静态库，不能用两套不同测试逻辑比较结果。
- 必须验证 C 写入的 KVDB/TSDB 可由 Rust 重启读取，Rust 写入的数据库可由 C 重启读取。
- 对确定性输入，双方生成的 sector 文件必须逐字节一致；只比较业务返回值不足以证明格式兼容。
- 双向验证必须覆盖二进制 blob、固定时间戳、迭代顺序、控制 getter、锁/解锁平衡和可观察打印输出。

## ABI-01 C ABI 必须精确兼容

- 原 C 测试使用到的公开符号必须由 release 静态库导出，并能由原头文件声明直接编译和链接。
- FFI 函数必须使用 `extern "C"`、稳定符号名和与 C 声明一致的参数/返回类型；需要时使用 `#[repr(C)]`。
- 指针的空值、长度、生命周期、别名和可写性必须在边界检查，内部立即转换为安全 Rust 表达。
- Rust panic 不得跨越 FFI 边界；边界必须转换为 C 能识别的错误码或失败结果。
- C 分配/C 释放、Rust 分配/Rust 释放不得交叉错配。

## MEM-01 默认使用安全 Rust

- 所有权数据使用 `Vec<u8>` 或固定数组，借用数据使用切片，可空语义使用 `Option`，错误使用 `Result`。
- 每次地址加法、长度相加、切片范围和指针转切片都必须先检查溢出与边界。
- 禁止 `static mut`；共享可变状态必须使用锁、原子类型或线程局部状态，并保持 C 的生命周期语义。
- `unsafe` 只能位于不可避免的 FFI 或底层边界，范围必须最小，并在附近写明安全前提。
- 禁止在生产代码中使用 `unwrap()`、`expect()`、`todo!()`、`unimplemented!()` 或占位实现。

## ERR-01 错误和输出参数语义必须保留

- 必须建立 C 错误码与 Rust 错误类型的完整映射，保留成功、未找到、无空间、读取失败、写入失败、校验失败等差异。
- C 输出参数只有在源实现会写入时才可修改；失败时是否保留旧值必须以 C 行为为准。
- 内部可以把输出参数改为 `Result<T, FdbErr>` 或 `Option<T>`，但 FFI 边界必须还原 C 调用约定。
- 禁止吞掉后端错误、用默认值代替错误或把不同错误统一成成功/未找到。

## CBK-01 回调和控制参数必须类型化且保持调用契约

- flash 回调应在安全核心中建模为 trait 方法，`void *` 控制参数应转换为有类型的枚举或结构。
- 必须保留回调调用次数、顺序、停止条件、用户上下文和回调返回值对控制流的影响。
- FFI 回调保存时间不得超过 C 生命周期保证；禁止长期持有未经证明有效的裸指针。
- 可选回调和空上下文必须显式建模，不能用伪地址或全局可变变量替代。

## GLB-01 全局状态、重入和并发边界必须明确

- 必须盘点 C 全局/静态状态，区分库状态、数据库实例状态和测试计数器。
- 实例状态必须归属对应 Rust 对象；测试计数器可使用 `thread_local!` 与 `Cell`，不得污染其他测试。
- 若 C 实现不保证线程安全，Rust 不得虚假宣称线程安全；若暴露 `Send`/`Sync`，必须有类型与同步证据。
- 初始化、反初始化、重复初始化和多实例互不干扰必须有测试。

## EVD-01 证据必须绑定当前输入和当前实现

- 成功证据必须由固定运行器生成 JSON 和日志，记录命令、退出码、时间、日志哈希、C 输入哈希和 Rust 目标哈希。
- 修改 `Cargo.toml`、`src/` 或 `tests/` 后，此前证据全部失效，必须冻结实现后重新运行。
- C case 行必须绑定包含准确 Rust 测试名的聚焦 `cargo test` 命令；API、模块和规范行必须绑定对应门禁命令。
- 禁止手写证据 JSON、复用失败日志、引用不存在的路径，或用自然语言 `PASS` 代替可校验证据。

## LOG-01 AI 交互和验证日志必须完整留存

- 必须把当前项目的完整 OpenCode 会话原始 JSON 导出到 `logs/trace/llm_chat_log.json`，不得删改、摘要或使用脱敏导出替代原记录。
- `logs/trace/trace-manifest.json` 必须记录会话 ID、OpenCode 版本、消息数量、会话文件哈希、C/Rust 哈希和验证产物索引。
- 构建、C 链接、双向兼容、覆盖率、API 和安全门禁的 JSON 与原始输出日志必须同步到 `logs/trace/verification/`。
- 最终判断必须重新检查源码、静态库、C/Rust 运行行为和持久化字节，不得采信会话文本中的“完成”“通过”或代理自评。

## VER-01 完成必须有独立证据

- 每个行为切片必须依次经过：C 证据、先失败的 Rust 验收测试、最小实现、聚焦测试、全量测试。
- 最终必须同时通过 Rust 构建、Rust 测试、原 C 测试链接运行、C case 覆盖、模块覆盖、规范合规、安全审计和占位审计。
- `reports/c-to-rust-compliance.tsv` 的每条规范必须为 `PASS` 并写出可定位到文件、测试、命令或运行轨迹的证据。
- 报告中的 `PASS` 不是证据本身；无法指出具体产物或结果时必须保持 `PENDING` 并继续工作。

## 强制产物格式

`reports/c-to-rust-compliance.tsv`：

```text
rule_id\tstatus\tevidence
BASE-01\tPASS\treports/evidence/final-source.json
```

`reports/c-module-coverage.tsv`：

```text
c_file\tc_symbols\trust_files\trust_tests\tevidence\tstatus
src/fdb_utils.c\tfdb_calc_crc32;_fdb_set_status\tsrc/layout.rs;src/crc.rs\tlayout_matches_c_probe;crc_matches_c_trace\treports/evidence/final-interop.json\tPASS
```

`reports/c-test-coverage.tsv` 的 `evidence` 必须指向运行准确 Rust 测试名的结构化 JSON；
`reports/c-api-coverage.tsv` 的 `evidence` 必须指向 C 链接或双向兼容门禁 JSON。
多个值使用分号分隔。证据必须具体且可复查，不得写 `N/A`、`TODO`、`TBD`、`skip`、“待完成”或泛化描述。
