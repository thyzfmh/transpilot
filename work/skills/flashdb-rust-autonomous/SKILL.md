# Autonomous Source Translation

## Load The Contract

Read these files in order:

1. `references/autonomous-source-translation-method.md` for the reusable method.
2. `references/c-to-rust-translation-spec.md` for C-to-Rust constraints.
3. `references/project-adapter.md` and the installed
   `harness/project-adapter.json` for current repository facts and commands.

The method and language constraints are reusable. The adapter is the only place
that may contain project-specific paths, build commands, configuration, and
verification entry points.

Do not ask the user questions. Do not delegate implementation. Continue until
the adapter's trusted completion command passes and `result/output.md` is
updated from machine-produced results.

## Non-Negotiable Rules

- Treat source behavior and source-native tests as the primary oracle.
- Do not use target-native tests as proof that source behavior is compatible.
- Do not modify the source project, this Skill, or the installed target harness.
- Do not guess ABI layout, integer width, persistent bytes, or callback behavior.
- Do not replace failed behavior with placeholders, fixed success, or weakened tests.
- Do not spend implementation time on reports while source acceptance is failing.
- Keep commands bounded and keep full output in files; print concise failure summaries.
- Persist the current work item and next action before changing implementation.

The current adapter binds immutable source files through
`references/source-manifest.sha256`; the installed source guard enforces it.

## Phase 0: Install And Discover

Use the project adapter to create or resume the target and install the fixed
harness. Preserve valid implementation files when resuming.

Install a fresh runtime copy of the fixed harness:

```bash
work/skills/flashdb-rust-autonomous/scripts/install_target_harness.sh
```

The repository stores the harness only under this Skill. The
`code/flashDB_rust/harness` directory is generated by the command above and
must not be treated as a submitted implementation artifact.

Then, from the target directory, run:

```bash
python3 harness/source_guard.py --target .
./harness/preflight.sh
python3 harness/project_discovery.py --target .
python3 harness/checkpoint.py init
python3 harness/c_coverage_check.py --init
python3 harness/api_surface_check.py --init
python3 harness/translation_spec_check.py --init
```

Run the unmodified source project's own tests through
`harness/source_oracle_runner.py`. It must clean and rebuild the original
implementation, mechanically account for every discovered source case, and
write `reports/source-oracle.json`. Confirm the source is healthy before
treating it as an oracle. Discovery must produce
`reports/project-profile.json`; do not manually invent the project inventory.

## Phase 1: Establish The Earliest Real Feedback

Before implementing high-level behavior:

1. Extract the public interface and required target artifact from the source.
2. Build a source-derived contract table for each reachable API: inputs,
   null/alias rules, outputs, error codes, state transitions, persistent writes,
   callbacks, and cleanup behavior.
3. Measure ABI-relevant sizes, alignments, field offsets, enum widths, and
   calling conventions when the language boundary requires them.
4. Create the smallest target that builds and exposes the complete interface.
5. Run `build_check.sh`, then run the adapter's source-native acceptance
   command against that exact registered artifact.
6. Record the first failing source case in the checkpoint.

The first source-native target run must happen as early as possible. Do not
first build a parallel target-only test suite. A link failure is useful feedback
and must be resolved before deeper implementation.

## Phase 2: Source-Native Test Loop

Repeat this loop:

```text
read checkpoint
  -> build and register one target artifact
  -> run the source-native acceptance gate against that same artifact
  -> select the first failed or not-run source case
  -> inspect its complete source test, helpers, production call path, and data contract
  -> derive expected results only from source assertions, formulas, or a source probe
  -> add a focused target test before the fix only when it transcribes that requirement
  -> implement the smallest source-equivalent behavior
  -> run the focused check
  -> rebuild, then rerun the source-native acceptance gate
  -> record passed count, first failure, and next action
```

Use:

```bash
./harness/build_check.sh
./harness/c_link_test.sh
python3 harness/c_coverage_check.py --progress
python3 harness/checkpoint.py show
```

`c_link_test.sh` stores complete suite logs and writes a machine-readable source
acceptance result. `c_coverage_check.py` derives coverage from that result. Do
not hand-edit source acceptance or coverage files.

Translate bottom-up. Close constants and integer formulas first, then byte
formats and backend I/O, then state machines, then public FFI wrappers. For the
current work item, inspect every source return/error path and every observable
write before coding. Do not replace a stateful C subsystem with a simpler Rust
collection unless source tests and source probes prove all observable
transitions, ordering, recovery, and persisted bytes remain equivalent.

After three failures caused by the same approach, change the approach: reduce
the behavior slice, create a source-side probe, inspect a lower-level path, or
replace the target design. Repeating the same analysis is not progress.

After a context compaction or continuation, read only the checkpoint and the
latest source-acceptance summary first. Run the recorded next command before
broadly rereading the repository.

## Phase 3: Contract Closure

Once every discovered source test passes against the target, close contracts
that source tests may not fully cover:

```bash
./harness/build_check.sh
python3 ./harness/source_oracle_runner.py
./harness/test_all.sh
python3 ./harness/differential_compare.py
python3 harness/api_surface_check.py
python3 harness/rust_policy_check.py
python3 harness/translation_spec_check.py
```

The applicable contracts come from discovery and the adapter, not from a
universal fixed list. For C-to-Rust library translation, they include compiled
constant values, public function signatures, measured C/Rust layout, callbacks,
error/output semantics, persistent compatibility, integer behavior, and panic
containment. Module closure is derived from the discovered source modules,
native suites, and current behavioral evidence; it must not be maintained as a
project-name-specific allowlist.

Persistent and external side effects are checked generically: run every
discovered native suite at least twice against the original implementation to
calibrate nondeterministic bytes, then once against the translated artifact
from an equivalent clean state. Compare case order, exit status, file
creation/deletion, sizes, and every source-stable byte. This reuses the source
project's own domain coverage instead of embedding project API names or
hand-written operation counts in the Skill.

If a contract change modifies target behavior, return immediately to the
source-native test loop. Do not continue preparing reports on a failing target.

## Phase 4: Evidence And Completion

Only after behavior and contract gates pass, freeze target source and generate
final evidence. The trusted completion command builds the final binary first,
then binds every behavioral record to that same source, target, adapter, and
static-library identity:

Internally, `final_verify.sh` uses `evidence_runner.py` to invoke adapter-defined
gates in order and seals the checkpoint only after all code-level checks pass.
The result is staged, the required interaction record is exported by
`trace_capture.py`, and only then is the result finalized.

```bash
work/skills/flashdb-rust-autonomous/scripts/final_verify_target.sh
```

Do not manually record `ready_for_final`. `checkpoint.py seal-final` is the only
operation allowed to create that state, and it succeeds only when every
adapter-required evidence record is current and valid.

`result/output.md` is generated by `completion.py` from the sealed checkpoint,
current acceptance counts, final report, and static-library hash. Trace export
happens after those artifacts exist; trace verification requires the exact
adapter-defined evidence and report set. Report success only when the trusted
completion command prints `TRUSTED_FINAL_VERIFY_PASS`.

## Blockers

A failing build, link, test, ABI check, or behavior check is not a blocker. Keep
repairing it.

If preflight exits with code `2`, attempt one repair and retry. Stop as
`BLOCKED` only after the same external condition occurs three consecutive
times. Record the command, all three failures, and required external action in
`result/output.md`.
